## 1. Diagnóstico Causal Concreto: Cronologia dos Timers e Fixture Leak

A causa raiz foi isolada com precisão matemática na **cronologia dos timers assíncronos do servidor mock HTTP no runner**, e **NÃO** em defeito do produto cliente:

### 1.1 Cronologia no Gate 29 (Opções de Câmera)
```
T = 0ms:      Runner dispara POST /api/replay (camera-options para Cam 1).
              Mock HTTP agenda timer de atraso: setTimeout(respondPost, 9000).

T = 8000ms:   Fetch no cliente aborta via AbortSignal.timeout(8000).
              Cliente entra em uncertainOp (botão e seletor travados).

T = 8600ms:   Runner acorda da espera literal de 8600ms.
              Runner executa segundo clique concorrente (postDelta = 0 verificado).
              Linha 1532: mockCameraOptionsDelayMs = 0 (apenas altera a variável para futuros POSTs!).
              O timer setTimeout(..., 9000) agendado em T=0 PERMANECE ATIVO no event loop do Node.js!

T = 8800ms:   Runner define mockCameraOptions['Cam 2 - Geral'] = ... (adversarial)
              e inicia espera de 1800ms para o polling passivo de background.

T = 9000ms:   CRASH CRONOLÓGICO: O timer de 9000ms do Node.js DISPARA!
              A função respondPost() (L432) é executada em background e aplica:
              mockCameraOptions['Cam 1 - Palco'] = { recordAudio: 'input', gainDb: -8, muted: true, offsetFrames: 12 }
              O próprio servidor mock aplicou a mutação de Cam 1 antes do teste avaliar Cam 2!

T = 10300ms:  Cliente executa GET /api/replay via setInterval(1500ms).
              O servidor mock retorna Cam 1 JÁ MUTADA!
              O cliente compara fresh.cameraOptions['Cam 1 - Palco'], constata igualdade,
              resolve determinísticamente (resolved = true), emite "Operação pendente confirmada..."
              e destrava o botão (#btn-save-cam-audio).

T = 10600ms:  Runner avalia gate29CrossCamCheck e encontra btnDisabled = false (FAIL).
```

### 1.2 Cronologia no Gate 31 (Auto-Align)
Idêntica dinâmica temporal:
* Em `T = 0ms`, o servidor agenda `setTimeout(respondPost, 26000)`.
* Em `T = 25000ms`, o cliente aborta por timeout e arma `uncertainOp`.
* Em `T = 25600ms`, o runner testa segundo clique e injeta calibração adversarial (`anchor: 'B'`, timestamp antigo).
* Em `T = 25800ms`, o runner inicia espera de 1800ms de polling passivo.
* **Em `T = 26000ms`:** O timer de 26000ms do Node.js dispara `respondPost()`, que **sobrescreve** `mockCalibration` com `anchor: 'A'` e timestamp atual (`Date.now()`).
* Em `T = 27300ms`, o polling passivo recebe a calibração legítima de `A`, o produto resolve legitimamente com `"Operação pendente confirmada pelo motor."` e destrava `#btn-auto-align`.

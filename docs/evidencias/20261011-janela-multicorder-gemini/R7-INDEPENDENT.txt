## 1. Diagnóstico Causal das Falhas de R5 (G11 e G22) e Validação dos Patches R7

A execução de R5 apresentou **24 PASS e 2 FAIL** estritamente delimitados em dois comportamentos assíncronos de interface:

### Falha 1: Gate 11 (`GATE_11_STOP_SUCCESS_TRANSITION`)
* **Mecanismo da Falha em R5:**
  Ao clicar em Stop, `handleStop()` definia corretamente `setStatus('MultiGravação finalizada.')`. Contudo, nos 800 ms de espera da asserção, o ciclo periódico de polling `fetchStatus(false)` retornava `rec: false`. Como `dirtyDraft === false`, `hasActiveError === false` e `uncertainOp === null`, a condição antiga executava cegamente `setStatus('Pronto para gravar.')`, apagando a mensagem de confirmação de parada antes da leitura do teste.
* **Correção Causal em R7 ([DRAFT-multicorder-r7.js#L164-L169](file:///D:/FreeMix-QA-Gemini-MultiCorder-20261011-0900/DRAFT-multicorder-r7.js#L164-L169)):**
  ```javascript
  } else if (!dirtyDraft && !hasActiveError && uncertainOp === null) {
    const cur = el('mc-status-text')?.textContent;
    if (!cur || cur === 'Conectando ao motor...' || cur === 'MultiGravação ativa.') {
      setStatus('Pronto para gravar.');
    }
  }
  ```
  O polling periódico agora só sobrescreve o texto com `"Pronto para gravar."` se a mensagem anterior era o estado inicial de conexão ou a transição direta de gravação ativa. Mensagens deliberadas de retorno ao operador (como `"MultiGravação finalizada."` e `"Status confirmado pelo motor..."`) são integralmente preservadas.

### Falha 2: Gate 22 (`GATE_22_PENDING_STOP_RESOLUTION_FLOW`)
* **Mecanismo da Falha em R5:**
  No Read 2 do Gate 22, o motor confirmava a parada tardia (`rec: false`). Ao acionar o botão Atualizar, `fetchStatus(true)` executava primeiro e, em [DRAFT-multicorder-r5.js#L135-L139](file:///D:/FreeMix-QA-Gemini-MultiCorder-20261011-0900/DRAFT-multicorder-r5.js#L135-L139), limpava `uncertainOp = null`. Em seguida, o listener de clique de `btn-refresh` tentava avaliar `if (uncertainOp === 'stop')`, que resultava em `false` porque a variável já havia sido consumida dentro de `fetchStatus`. Consequentemente, o bloco de sucesso nunca era executado, e a mensagem de erro do Read 1 (*"Motor confirmou gravação ainda ativa..."*) permanecia residualmente na tela.
* **Correção Causal em R7 ([DRAFT-multicorder-r7.js#L553-L574](file:///D:/FreeMix-QA-Gemini-MultiCorder-20261011-0900/DRAFT-multicorder-r7.js#L553-L574)):**
  ```javascript
  btnRefresh.addEventListener('click', async () => {
    const opBefore = uncertainOp;
    const freshState = await fetchStatus(true);
    if (freshState && typeof freshState.rec === 'boolean') {
      if (opBefore === 'start') { ... }
      else if (opBefore === 'stop') {
        if (freshState.rec === false) {
          uncertainOp = null;
          setStatus('Status confirmado pelo motor: gravação parada com sucesso.');
          renderControls();
        } else {
          setStatus('Motor confirmou gravação ainda ativa. Tente parar novamente quando o processo concluir.', true);
        }
      }
  ```
  Ao capturar `opBefore = uncertainOp` **antes** da chamada assíncrona de `fetchStatus(true)`, o listener retém com precisão a intenção da operação pendente. Quando `freshState.rec === false`, ele limpa a incerteza e atualiza afirmativamente a mensagem para `"Status confirmado pelo motor: gravação parada com sucesso."`, eliminando a mensagem de erro residual.
